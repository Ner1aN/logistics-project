# 03. Требования

## Функциональные требования

| ID | Требование |
|---|---|
| FR-01 | Система должна позволять пользователю авторизоваться. |
| FR-02 | Система должна позволять вести справочник клиентов. |
| FR-03 | Система должна позволять вести справочник водителей. |
| FR-04 | Система должна позволять вести справочник транспортных средств. |
| FR-05 | Система должна позволять создавать заявку на перевозку. |
| FR-06 | При создании заявки менеджер должен выбрать статус заявки. |
| FR-07 | Система не должна автоматически назначать статус заявки по умолчанию вместо менеджера. |
| FR-08 | В заявке должна быть указана хотя бы масса или объем груза. |
| FR-09 | Система должна позволять выбрать тип груза: песок, щебень или бетон. |
| FR-10 | Если стоимость не указана вручную, система должна рассчитать ее автоматически. |
| FR-11 | Если стоимость указана вручную, система не должна перезаписывать ее автоматическим расчетом. |
| FR-12 | Система должна позволять назначать на одну заявку одно или несколько ТС. |
| FR-13 | Для каждого назначения ТС система должна хранить водителя, транспорт, число рейсов и километраж по трем плечам. |
| FR-14 | Система должна учитывать занятость водителя и не позволять назначить занятого водителя в другую активную перевозку. |
| FR-15 | Система должна учитывать занятость ТС и не позволять назначить занятое ТС в другую активную перевозку. |
| FR-16 | Система должна учитывать грузоподъемность ТС и показывать суммарное покрытие груза назначенными машинами. |
| FR-17 | Система должна рассчитывать общий километраж перевозки по трем плечам маршрута и количеству рейсов. |
| FR-18 | Система должна учитывать стоимость километража в итоговой стоимости заявки. |
| FR-19 | Система должна фиксировать историю изменения статуса заявки. |
| FR-20 | Система должна архивировать завершенные и отмененные заявки. |
| FR-21 | Система должна предоставлять список активных заявок и отдельный архив. |
| FR-22 | Система должна предоставлять отчетность по заявкам, статусам, перевозкам и загрузке водителей. |
| FR-23 | Система должна экспортировать отчеты в PDF. |
| FR-24 | Система должна экспортировать отчеты в Excel. |
| FR-25 | Система должна предоставлять демоданные для презентации и тестирования. |

## Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-01 | Интерфейс должен быть реализован в едином Bootstrap-стиле. |
| NFR-02 | Система должна запускаться локально без сложной инфраструктуры. |
| NFR-03 | Для локального запуска должна использоваться SQLite. |
| NFR-04 | Бизнес-логика должна быть покрыта автоматическими тестами. |
| NFR-05 | Валидационные ошибки должны отображаться пользователю понятным текстом. |
| NFR-06 | Отчеты должны быть доступны через веб-интерфейс без ручной работы с БД. |
| NFR-07 | Система должна сохранять целостность связей между заявками, клиентами, водителями и ТС. |
| NFR-08 | Проект должен иметь понятную структуру для учебной демонстрации и защиты диплома. |
| NFR-09 | Система должна сохранять историю изменений статусов для аудита. |
| NFR-10 | Формирование демоданных должно быть повторяемым. |

## Ограничения

- Расстояние по маршруту не рассчитывается автоматически через карты.
- Километраж вводится менеджером вручную.
- Водитель не имеет отдельного личного кабинета.
- Интеграции с внешними сервисами в текущей версии не реализованы.
- API описан как возможное развитие системы, текущий интерфейс построен на Django Templates.
- Расчет стоимости использует фиксированные тарифы в коде, без отдельной таблицы тарифов.

## Предположения

- Менеджер знает корректные данные клиента и груза.
- Менеджер выбирает статус заявки осознанно.
- Данные по километражу берутся из внешнего источника: карты, путевого листа или расчетов логиста.
- Один водитель и одно ТС не могут быть одновременно заняты в двух активных перевозках.
- Завершенные и отмененные заявки не требуют дальнейшего назначения ресурсов.
